# Database Schema

The platform uses three tables. Schema is auto-generated by Hibernate
(`ddl-auto: update`) from the JPA entities in
`backend/src/main/java/com/healthcare/appointment/entity/`, so this document
mirrors — and must stay in sync with — those entity classes.

## `users`

| Column      | Type          | Constraints                  |
|-------------|---------------|-------------------------------|
| id          | BIGINT        | PK, auto-increment            |
| full_name   | VARCHAR(100)  | NOT NULL                      |
| email       | VARCHAR(150)  | NOT NULL, UNIQUE               |
| password    | VARCHAR       | NOT NULL (BCrypt hash)         |
| created_at  | TIMESTAMP     | NOT NULL                      |

## `slots`

Represents a bookable appointment slot (doctor + date + time window).

| Column       | Type          | Constraints                  |
|--------------|---------------|--------------------------------|
| id           | BIGINT        | PK, auto-increment             |
| doctor_name  | VARCHAR(100)  | NOT NULL                       |
| department   | VARCHAR(100)  | NOT NULL                       |
| slot_date    | DATE          | NOT NULL                       |
| start_time   | TIME          | NOT NULL                       |
| end_time     | TIME          | NOT NULL                       |
| status       | VARCHAR(20)   | NOT NULL, `AVAILABLE` \| `BOOKED` |
| version      | BIGINT        | optimistic-lock version column |
| created_at   | TIMESTAMP     | NOT NULL                       |

## `appointments`

Links a user to a slot. Rows are **never deleted** — cancelling an
appointment sets its status instead — so this table doubles as the
appointment history log.

| Column         | Type        | Constraints                        |
|----------------|-------------|-------------------------------------|
| id             | BIGINT      | PK, auto-increment                  |
| user_id        | BIGINT      | FK → users(id), NOT NULL            |
| slot_id        | BIGINT      | FK → slots(id), NOT NULL            |
| status         | VARCHAR(20) | NOT NULL, `BOOKED` \| `CANCELLED`   |
| booked_at      | TIMESTAMP   | NOT NULL                            |
| cancelled_at   | TIMESTAMP   | NULL until cancelled                |

## Relationships

```
users (1) ───< (many) appointments (many) >─── (1) slots
```

- One user can have many appointments (across time / history).
- One slot has at most one **active** (`BOOKED`) appointment at a time,
  enforced at the application layer (see below) rather than a DB
  constraint, because a slot legitimately accumulates multiple historical
  appointment rows over time (booked → cancelled → booked again by someone
  else).

## Duplicate booking / concurrency safety

Booking is handled in `AppointmentService.createAppointment`:

1. The target `Slot` row is fetched with a `PESSIMISTIC_WRITE` lock
   (`SELECT ... FOR UPDATE`), so only one transaction can inspect/modify
   that row at a time.
2. If `slot.status != AVAILABLE`, the request is rejected with
   `SlotAlreadyBookedException` (mapped to HTTP 409).
3. Otherwise the slot is flipped to `BOOKED` and the `Appointment` row is
   inserted, all within the same transaction.

If two requests race for the same slot, the second one blocks on the row
lock until the first transaction commits, then re-reads the row and
correctly sees `BOOKED` — so it fails instead of double-booking. This is
covered by `ConcurrentBookingTest`.

Cancelling an appointment reverses this: the appointment is marked
`CANCELLED` and the slot is flipped back to `AVAILABLE`, using the same
locking strategy.
